# 백업·복구 운영 절차

## 현재 기준과 목표

- 현재 Supabase 조직 플랜: Free(2026-08-12 확인). 자동 일일 백업 복구를 출시 보장으로 간주하지 않습니다.
- 출시 최소 목표: RPO 24시간, RTO 8시간
- 권장 상용 목표: Supabase Pro 일일 백업 + 별도 논리 백업, RPO 24시간 / RTO 4시간
- 중요 배정 기간에 24시간 손실도 허용하기 어렵다면 PITR 도입을 별도 승인합니다.

## 백업

- 매일 02:00 KST: `supabase db dump --db-url "$DATABASE_URL" -f ngnx-YYYYMMDD.sql` 실행
- 결과는 AES-256 서버측 암호화가 적용된 별도 저장소에 30일 보관합니다.
- DB 접속 URL은 CI 비밀 저장소에만 보관하고 로그·저장소에 출력하지 않습니다.
- 주 1회 백업 파일 크기, 암호화, 체크섬, 최근 성공 시각을 점검합니다.

## 복구

1. 장애 범위와 마지막 정상 시각을 기록하고 쓰기 작업을 중지합니다.
2. 새 격리 Supabase 프로젝트에 최신 정상 백업을 복구합니다.
3. 사용자·수업·모집·응답·배정·알림의 건수와 FK 무결성을 검증합니다.
4. 관리자 로그인 → 수업 조회 → 강사 조회 → 배정 조회의 읽기 점검을 수행합니다.
5. 서비스 환경변수를 복구 프로젝트로 전환하고 스모크 테스트 후 쓰기를 재개합니다.
6. 원인, 실제 RPO/RTO, 유실 범위, 재발 방지를 사고 기록에 남깁니다.

## 훈련과 책임

- 담당: 최고관리자(승인), 운영관리자(실행), 개발 담당(기술 복구)
- 분기 1회 격리 프로젝트 복구 훈련을 수행하고 실제 소요시간과 증거를 QA 문서에 연결합니다.
- 첫 운영 출시 전 최소 1회의 전체 복구 훈련이 필요합니다.

## Vercel/Sites 애플리케이션 롤백

- DB 마이그레이션은 이전 버전 앱과 호환되는 추가형 변경을 우선합니다.
- 앱 장애는 직전 정상 배포를 재승격하고, DB 변경은 데이터 손실 없는 별도 보정 마이그레이션으로 되돌립니다.
- 운영 DB에 `DROP`, 대량 `DELETE`, 열 타입 축소를 직접 실행하지 않습니다.
